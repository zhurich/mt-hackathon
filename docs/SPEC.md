## 1. Цель

Интерактивный геймифицированный тренажёр для проводников высокоскоростной магистрали (ВСМ Москва — Санкт-Петербург).
Сотрудник проходит нештатные ситуации на борту, принимает решения под таймером, видит последствия
по двум шкалам — «Лояльность пассажира» и «Рейтинг безопасности» — и получает очки компетенций,
уровни, достижения и место в рейтинге. После каждого сценария — обучающий разбор каждого решения
со ссылкой на регламент.

## 4. Предметная область (из датасета)

Источники: `Ситуации на борту.pdf` (51 ситуация + ролевая модель), `СТО РЖД 03.011-2026` (обслуживание на ВСМ),
`СТО РЖД 03.013-2026` (оснащённость вагонов), `СТО РЖД 03.014-2026` (маломобильные пассажиры), `Классы обслуживания ВСМ.pdf`.

- **Маршрут:** Москва — Тверь — Великий Новгород — Санкт-Петербург, скорость до 400 км/ч, стоянки ~1 мин.
- **Классы обслуживания:** `standard` (3+2), `comfort` (2+2, игровая комната, дети 10–16 без сопровождения),
  `business` (2+2, плед, питание, планшет), `first` (2+1, персональный подход).
  Допустимое ожидание обслуживания: стандарт 20 мин, комфорт 15, бизнес 10, первый 5 (СТО 03.011 п. 10.5).
- **Бригада:** проводник, начальник поезда (НП), бортинженер, сотрудники подразделения транспортной безопасности (ПТБ),
  при необходимости — полиция (ЛОВД), медики на станции.
- **Ролевая модель общения** (ключевая для оценки soft skills):
  1. `acknowledge` — **Признать ситуацию** («Я Вас понимаю…», «Сожалею, что это доставило дискомфорт…»)
  2. `rule` — **Обозначить правило** («Обращаю Ваше внимание, что…»)
  3. `solution` — **Предложить решение** («Я уточню и вернусь к Вам…», «Я приглашу начальника поезда…»)
  4. `assure` — **Заверить** («Благодарю Вас за понимание…»)
- **Важные нюансы регламентов,** на которых строятся развилки:
  - по рации не сообщать, что пассажир пьян — чтобы не провоцировать агрессию (сит. 6);
  - не выдавать личные лекарства (сит. 28), вызывать НП, объявлять о медиках среди пассажиров, медиков — на ближайшую станцию;
  - бесхозную вещь не трогать, сообщить НП и ПТБ по поездной радиосвязи (сит. 41);
  - потерявшийся ребёнок: оставаться рядом, объявление без лишних персональных данных (сит. 30);
  - два пассажира на одно место: проверить документы, пригласить НП, не занимать сторону (сит. 23, 33);
  - курение (в т.ч. вейп) — угроза безопасности движения, при отказе — НП/ПТБ (сит. 20);
  - МГН: помощь при размещении, кресло-коляска в поезде, заказ питания на место (СТО 03.014 п. 6.5, 8.7, 8.8).

## 6. Движок сценариев

Полный формат — в [`docs/scenario-format.md`](scenario-format.md). Кратко:

- **Сценарий** = метаданные + начальное состояние (`loyalty`, `safety`, `vars`) + граф `nodes` + `interrupts`.
- **Типы узлов:**
  - `choice` — реплика/ситуация + варианты ответа; опционально `timer` (сек) и `on_timeout`;
  - `router` — невидимый узел: выбирает следующий узел по условиям от состояния (шкалы, флаги, переменные, класс вагона);
  - `ending` — финал с исходом `success | partial | fail`.
- **Вариант ответа:** текст, `effects` (изменения `loyalty`, `safety`, `vars`, `flags`), `quality` (`best|good|poor|bad`),
  `role_model` (какие шаги модели реализует), `feedback` (почему так), `next`, опционально `if` (условие доступности).
- **Прерывания (`interrupts`):** проверяются после каждого шага; если условие выполнено (например, `safety <= 15`),
  сценарий принудительно переходит в указанный узел. Так шкалы реально управляют сюжетом.
- **Таймер:** сервер фиксирует момент показа узла. Ответ, пришедший позже `timer + 2 с` (сетевой запас), или явный таймаут
  с клиента — обрабатываются веткой `on_timeout` (свои эффекты и следующий узел). Время реакции пишется в лог.
- **Состояние попытки:** `node_id`, `loyalty`, `safety`, `vars`, `flags`, `path` — хранится в БД (`attempts.state`), backend stateless.

### Алгоритм шага (`engine/runtime.py`)
1. Проверить, что попытка активна и узел — `choice`.
2. Определить таймаут (явный или по серверному времени).
3. Выбрать ветку: вариант (проверив его `if`) или `on_timeout`.
4. Применить `effects`, ограничить шкалы диапазоном 0..100.
5. Записать решение в `path` (узел, вариант, эффекты, время реакции, качество, компетенции, шаги ролевой модели).
6. Проверить `interrupts` → при срабатывании перейти в их `next`.
7. Иначе перейти в `next`; пока текущий узел `router` — вычислить его маршрут.
8. Если узел `ending` — завершить попытку и запустить подсчёт результатов (п. 7).

## 7. Подсчёт результатов (`engine/scoring.py`)

Все константы в одном месте — `scoring.py`.

- **Качество решения → балл:** `best = 1.0`, `good = 0.6`, `poor = 0.2`, `bad = 0.0`, таймаут = `0.0`.
- **Очки компетенций за попытку:** для каждого решения и каждой компетенции узла: `round(10 × quality)`.
- **XP за попытку:** `сумма очков компетенций` + `бонус исхода` (`success: 30 × difficulty`, `partial: 15 × difficulty`, `fail: 0`)
  + `бонус скорости` (+2 за каждое решение `best`, принятое быстрее половины таймера).
- **Результат по компетенции в попытке:** среднее качество решений, помеченных этой компетенцией (0..100).
- **Мастерство по компетенции (профиль):** экспоненциальное сглаживание по попыткам: `new = 0.5 × old + 0.5 × result`
  (первая попытка — просто `result`). ≥ 75 — «освоена», < 50 — «проседает».
- **Покрытие ролевой модели:** какие из 4 шагов встретились в выбранных коммуникативных вариантах.

## 8. Геймификация (`gamification/*`)

- **Уровни** (по суммарному XP, не сгорает): Стажёр (0) → Проводник III класса (150) → Проводник II класса (400)
  → Проводник I класса (800) → Старший проводник (1300) → Наставник (2000) → Эксперт ВСМ (3000).
- **Активные баллы** = XP, заработанный за последние 30 дней. Они **сгорают** и определяют место в рейтинге —
  стимул тренироваться регулярно. За 5 дней до сгорания — уведомление.
- **Рейтинг:** области `brigade` (моя бригада), `depot` (моё депо), `company`; сортировка по активным баллам.
- **Достижения:** `backend/content/achievements.yaml`; тип правила + параметры. Типы правил реализованы в `achievements.py`
  (новая ачивка существующего типа = только YAML).
- **Челленджи:** `backend/content/challenges.yaml`; период действия + правило + награда XP.
- **Уведомления:** новый сценарий, новый челлендж, выполненный челлендж, новое достижение, новый уровень, сгорающие баллы.
  Хранятся в БД, frontend опрашивает раз в 30 с.

## 9. Аналитика (`analytics/*`)

- **Сотрудник:** мастерство по 7 компетенциям, освоенные/проседающие компетенции, динамика XP, средние шкалы,
  доля таймаутов, среднее время реакции, покрытие ролевой модели, **текстовые выводы** (правила вида
  «40 % решений в медицинских сценариях — таймауты → тренируйте скорость реакции») и **рекомендованные сценарии**
  по слабым компетенциям.
- **Тренер (роль `trainer`):** сводка по бригадам и депо (среднее мастерство по компетенциям), «самые сложные решения»
  (узлы с наибольшей долей плохих ответов и таймаутов), таблица сотрудников.
- **Сырые события:** журнал решений (`attempt_events`) доступен через API интеграции.

## 11. Модель данных

`org_units` (депо/бригады), `users` (login, псевдоним, табельный код, роль, бригада, внешний id для HR),
`scenarios` (id, версия, данные JSON, опубликован), `attempts` (пользователь, сценарий, статус, состояние, итоги),
`attempt_events` (каждое решение), `xp_grants` (начисления XP с датой — для сгорания), `user_competencies`,
`user_achievements`, `user_challenges`, `notifications`, `api_keys` (хэш ключа).

## 12. Безопасность и соответствие 152-ФЗ

- В БД и в сценариях нет реальных ПДн: пассажиры обезличены («пассажир места 7А»), сотрудники — синтетические псевдонимы.
- У сотрудника хранится минимум: логин, псевдоним, табельный код, роль, бригада.
- Секреты (`JWT_SECRET`, API-ключи) — только через переменные окружения; в репозитории — `.env.example`.
- API-ключи интеграций хранятся в виде SHA-256.
- Ошибки не раскрывают внутренности; некорректные действия (ответ в завершённой попытке, чужая попытка,
  недоступный вариант) → понятные коды 4xx.
- Подробности — `docs/security.md`.
